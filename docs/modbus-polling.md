## 1. 定位

轮询调度是采集线程内的 **Modbus 主站逻辑层**：通过通道抽象层接口，对节点注册表中的每个从站周期性地发起「读保持寄存器（功能码 0x03）」请求，完成应答校验、数据快照更新、超时重试与离线判定。数据产出喂给处理域共享队列。

```
通道抽象层（#3）  ←  轮询调度层（本文）  →  处理域队列（#5 待补）
   send/recv          组装帧 · CRC · 轮转 · 超时 · 离线判定      原始数据帧
```

## 2. 轮询周期与时序参数（先给结论）

| 参数 | 取值 | 设计依据 |
|---|---|---|
| 轮询周期 | **2s**（整轮所有节点各询一次） | 环境量缓变；SHT30 采样 100ms，余量充足；与 UI 刷新/MQTT 上报节奏对齐 |
| 单节点应答超时 | **200ms** | 正常一问一答约 30ms，留 6~10 倍余量防总线抖动 |
| 连续失败离线阈值 | **3 次** | 1~2 次可容忍瞬时干扰；3 次连续无应答视为真离线 |
| 离线节点降频 | 每 5 轮询 1 次 | 死节点不拖累在线节点刷新节奏 |
| 离线恢复 | 成功应答 1 次即恢复 ONLINE | 环境监测业务容忍短暂抖动，恢复要快 |
| 帧间静默 | ≥3.5 字符时间（@9600 ≈ 4ms） | Modbus RTU 标准规定的帧分隔 |
| 时间基准 | CLOCK_MONOTONIC | 单调时钟，避免系统时间被 NTP/手动修改导致调度漂移 |

**单节点一问一答耗时预算（@9600 8N1，1 字节 ≈ 1.15ms）：**

| 环节 | 耗时 |
|---|---|
| 请求帧 8B 发送（地址+功能码+地址2B+数量2B+CRC2B） | ≈ 9.2ms |
| 从站处理 + 应答 9B 接收（数据 2B×N+CRC） | ≈ 12~15ms |
| 帧间静默 3.5 字符 | ≈ 4ms |
| **单节点合计** | **≈ 25~30ms** |

- 3 个节点整轮 ≈ **90ms**，占 2s 周期的 **< 5%**——余量非常充足
- 因此 200ms 超时完全不会误伤正常节点，200ms 是「容忍异常」而非「正常等待」

> 面试点：这个时间预算表就是回答「轮询周期为什么取 2s、超时为什么取 200ms」的底气——每个数字都能讲出推导过程，不是拍脑袋。

## 3. 调度状态机

```
                ┌─────────────────────────────────────────────┐
                │                    IDLE                      │
                │  等到下一个轮询时隙（用绝对时间点，防漂移）    │
                └──────────────────────┬──────────────────────┘
                                       │ 取下一节点（轮转）
                                       ▼
                ┌─────────────────────────────────────────────┐
   fail<3 ───── │               SEND_REQUEST                   │
                │  组装 0x03 帧 → ch->send()                   │
                └──────────────────────┬──────────────────────┘
                                       │ 发送成功
                                       ▼
                ┌─────────────────────────────────────────────┐
                │              WAIT_RESPONSE                   │
                │  ch->recv(timeout=200ms)                     │
                └───┬───────────────────────────┬──────────────┘
                    │ 成功收帧                   │ 超时 / 错误
                    ▼                           ▼
     ┌────────────────────────┐    ┌─────────────────────────┐
     │  CRC16 校验 → 异常码检查 │    │  fail_count++           │
     │  解析数据 → 更新 regs 快照│   │  fail>=3 → OFFLINE      │
     │  fail_count=0 → ONLINE  │    │  + 记录断联事件(时间戳)   │
     │  (曾离线 → 记恢复事件)    │    │  -EIO → 重初始化通道      │
     └────────────┬───────────┘    └────────────┬────────────┘
                  └───────────┬─────────────────┘
                              ▼
                         回到 IDLE（下一节点）
```

**节点调度顺序：round-robin 轮转**

- 节点表按 `addr` 升序排列，每轮从上一轮的下一节点开始，公平轮询
- 离线节点进入**降频队列**：仍按轮转顺序，但跳过 4 次只询 1 次（每 5 轮出现一次），在线节点保持 2s 满节奏

## 4. 应答校验与解析规则

| 校验项 | 规则 | 失败处理 |
|---|---|---|
| 帧长度 | 请求 8B / 应答 ≥ 9B，地址匹配 | 丢弃，计失败 |
| CRC16 | 全帧校验（多项式 0xA001） | 丢弃，计失败 |
| 功能码回显 | 应答功能码 = 0x03 | 不符，计失败 |
| 异常帧 | 功能码高位 = 0x83 + 异常码（01 非法功能 / 02 非法地址 / 03 非法数据） | 记日志 + 计失败（异常码入日志，便于定位节点固件问题） |
| 数据长度 | 数据字节数 = 寄存器数 × 2 | 不符，计失败 |

**解析落点**：按 §4.1 寄存器映射表写入 `node->regs[]`（40001 温度 / 40002 湿度 / 40003 烟雾 / 40004~07 电压电流 / 40008 状态字），带时间戳打包进共享队列 → 处理域。

## 5. 离线语义与数据缺失标记（承接"失联策略"）

- **离线判定**：连续 3 次超时 → 节点 OFFLINE
- **离线动作**：
  1. 记录**断联事件**（节点 ID + 首次离线时间戳）到 SQLite 的 `event_log`（待补 #6 表结构）
  2. 该节点数据在后续快照中标记 `NODE_OFFLINE`，处理域不再外报其数据，UI 显示离线态
  3. 进入降频轮询
- **恢复**：任意一次成功应答 → ONLINE + 记录恢复事件 → 恢复正常节奏，数据自动接回
- **与云端的衔接**：网关断网时历史由 SQLite 补传（已有设计）；**节点离线期间不产生数据，不存在补传**——空缺由 UI/云端标注"离线时段"，这就是之前定的"周期采样业务可容忍丢数"策略的落地

## 6. 面试价值点

1. **参数推导能力**：周期/超时/阈值每个参数都有时间预算支撑，体现工程思维而非拍脑袋
2. **状态机设计**：轮询调度是典型有限状态机，可与 MQTT 重连状态机、告警状态机对照讲解
3. **故障隔离**：离线降频 + 单节点失败不影响整轮调度——分布式系统可用性设计
4. **单调时钟**：CLOCK_MONOTONIC 选择背后的原因（系统时间可变性），细节见功力
5. **协议细节**：CRC16、帧间静默 3.5 字符、异常码语义——Modbus 协议真的吃透了

**简历 bullet 参考：**
> 实现 Modbus RTU 主站轮询调度：基于时间预算设计 2s 周期 / 200ms 超时 / 3 次离线判定，故障节点降频隔离，在线节点不中断；单调时钟调度防系统时间漂移。
