## 1. 定位与链路总览

MQTT 线程是网关的"上云出口"：把处理域的归一化数据按物模型上报，把告警事件即时推送；断网时数据进 `cache_queue`，恢复后按序补传。**连接可靠性是本节主题——重连策略决定"看起来掉线了还是真的掉线了"。**

```
处理线程 ──(归一化数据/告警事件)──► 上报队列 ──► MQTT 线程
                                                  ├─ 在线：聚合上报(5s) + 事件即时上报
                                                  └─ 断网：数据入 cache_queue（存储域）
                                                          ↓ 重连成功
                                                  先补传存量 → 切回实时上报
```

## 2. 连接参数与鉴权（OneNET 三要素）

| 项 | 值 | 说明 |
|---|---|---|
| Broker | `mqtt.heclouds.com:1883` | TCP 明文（生产可换 8883 TLS，本项目 1883 足够） |
| ClientID | 设备名称 | OneNET 三要素鉴权 |
| Username | 产品 ID | 创建产品时生成 |
| Password | 设备密钥 | 设备注册时生成 |
| KeepAlive | **60s** | 协议层心跳，broker 超时踢连接 |
| QoS | **1**（上报）；0（可选） | 至少一次投递 + 应用层幂等 |
| CleanSession | **false（0）** | 断线重连后不丢订阅（本项目无订阅需求，但保默认一致性） |
| LWT 遗嘱 | 可选：`offline` 事件 | broker 检测到异常掉线时发布，正常退出不发——"真离线"通知 |

> 面试点：**KeepAlive 是协议层保活，LWT 是异常离线通知**——两者一主动一被动，是 MQTT 连接可靠性的一对经典组合。CleanSession=0 保证会话续传语义，能讲清这三个概念，MQTT 基础就过关了。

## 3. 上报内容与节奏

### 3.1 属性上报（周期数据）——聚合策略

- **每 5s 一次，把所有在线节点的最新快照合并进一次 `property/post`**
- 报文结构（OneNET 物模型，一条消息多个属性/多节点）：

```json
{
  "id": "msg_20260817_144500_001",
  "version": "1.0",
  "params": {
    "node1_temp":  { "value": 25.3 },
    "node1_humi":  { "value": 61.2 },
    "node1_smoke": { "value": 0.42 },
    "node1_volt":  { "value": 219.8 },
    "node1_curr":  { "value": 12.4 },
    "node2_temp":  { "value": 26.1 }
  }
}
```

**为什么聚合而不是 2s 单条：** 环境量 2s 才变一点，5s 聚合足够；一次报文带多节点多属性，broker 压力、云端存储、流量成本（OneNET 按条计费）都显著下降。**2s 采集精度 → 5s 上报节奏**，这个"精度与成本的取舍"面试官喜欢听。

### 3.2 事件上报（告警/恢复）——即时策略

- 告警状态机每次转移（进入/恢复）**立刻**发 `thing/event/post`，不等待 5s 聚合——告警要快，不能攒
- 事件报文带：节点、指标、级别、当前值、阈值、时间戳

```json
{
  "id": "evt_20260817_144512_003",
  "version": "1.0",
  "params": { "eventType": "alarm", "nodeId": 1, "metric": "temp",
              "level": 2, "value": 55.3, "threshold": 55.0 }
}
```

- 上报成功后本地 `alarm_log` 标记"已上云"（可选，便于对账）
- 补传期间发生的告警同样入 cache_queue，按序补

### 3.3 QoS 语义与去重

- QoS1 = **至少一次**：可能重复投递 → 应用层必须幂等
- 云端/对账侧按 **(node_id, ts)** 去重（与 storage-design.md 的补传幂等键一致，一套键贯穿本地与云端）

> 面试点：QoS1 + 应用层幂等是标准组合——"QoS 选型为什么不用 0/2"的标准答法：0 会丢（不可接受），2 有握手开销（没必要），1 配合幂等恰好。

## 4. 断线重连状态机

```
                    ┌─────────── 断线（socket错误/keepalive超时）
                    ▼
        ┌──────────────┐   connect失败或超时(5s)   ┌──────────────┐
        │  CONNECTED   │ ───────────────────────► │ RECONNECTING │
        └──────────────┘                          └──────────────┘
            ▲    │                                          │
            │    └────────── 正常上报/心跳 ──────────────    │
            │             (状态不变)                        │
            └────────────── connect成功 ────────────────────┘
                     ↓ 重连成功进入补传流程（见 §5）
```

**重连参数（指数退避 + 抖动）：**

| 项 | 值 | 说明 |
|---|---|---|
| 首次重试 | 1s | 可能只是瞬时抖动 |
| 退避倍率 | ×2 | 1s → 2s → 4s → 8s → 16s |
| 封顶 | 30s | 不再翻倍，防长时间空转 |
| 抖动 | ±20% 随机 | 多网关同时掉线时不"同时重连"（同步风暴） |
| connect 超时 | 5s | 单次尝试不无限等 |

- 连续失败计数持续累加 → 供 UI 状态栏显示"重连中(N)"（与 lvgl-ui.md 状态栏衔接）
- 重连成功：计数清零 → 进入补传流程 → 完成后切实时

> 面试点：**指数退避 + 抖动 + 封顶**是分布式系统重连的标配，也是"为什么不能固定 5s 死循环重试"的答案（固定重试会放大服务端压力、并发风暴）。

## 5. 离线补传流程（与 cache_queue 衔接）

### 5.1 断网时（写入侧）

- 检测到断网（连接断开）→ 置 `online=0` 标志
- 处理线程的数据**照常进 SQLite node_data**，同时每条按物模型 JSON 写入 `cache_queue`（status=0）——存储域已定，这里只定触发时机
- **实时上报停止，但采集/处理/存储不受影响**——这是网关断网不慌的底气

### 5.2 恢复时（补传侧）——先存量，后实时

```
重连成功 → 置 online=1
  → 循环：SELECT * FROM cache_queue WHERE status=0 ORDER BY ts ASC LIMIT 20
     → 逐条 publish(QoS1)
     → 成功 → status=1；失败(retry>5) → 保留，等下轮
  → 队列清空（或本轮处理完）→ 切回实时聚合上报
```

- **顺序：先旧后新**（ORDER BY ts ASC），云端时间线不乱
- **批量限流**：每轮最多 20 条，防止断网一周（≈120 万条/3.5MB 数据换算…实际 5s 粒度≈12000 条）一次性刷爆 broker
- **幂等**：每条报文带原始采集 ts，云端按 (node_id, ts) 去重，重传无害
- **补传期间的新数据**：直接实时上报（不重复入队）——队列只装"断网期间"的存量
- 已传记录（status=1）超保留期由清理任务删除（storage-design.md §3.3）

> 面试点：补传的**限流分批**（一次刷 1 万条 vs 每轮 20 条）和**新旧衔接**（先存量后实时、新数据不入队），是断点续传设计的两个实操细节，面试官问"断网一周会怎样"就靠这段答。

## 6. 线程模型与数据流

| 环节 | 设计 |
|---|---|
| 库选型 | paho-mqtt-c（**异步 API**，回调驱动）——不阻塞线程，断线由回调通知 |
| MQTT 线程 | 单线程事件循环：connect / publish / 断线重连 / 补传调度 |
| 输入 | 上报队列（处理线程推入）：周期数据 + 事件数据两类，事件优先 |
| 输出 | `cache_queue`（断网时）、broker（在线时） |
| 与 UI 衔接 | `online` 状态位 + 重连计数 → 状态栏（lvgl-ui.md） |
| 与存储衔接 | 重连成功先读 cache_queue 补传，再切实时 |

## 7. 面试价值点

1. **三要素鉴权 + 物模型 Topic**：OneNET 接入全流程，协议层实战
2. **聚合上报 vs 事件即时**：周期数据攒批降成本、告警即时保实时——两类数据两种策略
3. **QoS 选型**：QoS1 + 幂等去重 = 至少一次投递的标准解
4. **指数退避重连**：防重连风暴、抖动防同步、封顶防空转
5. **断点续传**：限流分批 + 先旧后新 + 新数据不入队——完整补传工程
6. **KeepAlive/LWT/CleanSession**：MQTT 连接语义三件套

**简历 bullet 参考：**
> 基于 paho-mqtt 接入 OneNET：物模型属性聚合上报（5s）与告警事件即时推送（QoS1 + 幂等去重）；实现指数退避重连（1s~30s 封顶 + 抖动防同步风暴）与断网补传（cache_queue 先旧后新、分批限流、恢复后先存量后实时）。
