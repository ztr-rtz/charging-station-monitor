## 1. 定位与总体布局

800×480 是 4.3 寸屏的典型分辨率，UI 做成**多页面 + 顶部常驻状态栏**。主交互是页面切换（按键/触摸），不做复杂动效——嵌入式工业屏以"信息密度和可读性"为先。

```
┌────────────────────────────────────────────────────┐
│ 状态栏(40px)  ⏱ 14:32:05  ●节点2在线  ○MQTT已连接 │  ← 常驻，所有页面共享
├────────────────────────────────────────────────────┤
│                                                    │
│                页面内容区 (440px)                   │
│          页面1 实时仪表盘 / 页面2 历史曲线           │
│          页面3 告警记录 / 页面4 系统状态             │
│                                                    │
├────────────────────────────────────────────────────┤
│ 底栏(0~40px)  [节点1] [节点2]  ←节点切换(仅仪表盘)  │
└────────────────────────────────────────────────────┘
```

**状态栏语义（面试可讲）：**
- 时间：本地时间，1s 刷新
- 节点在线：聚合所有节点的在线/离线状态，离线闪烁黄标
- MQTT 状态：已连接/重连中/断网——把网络状态可视化，也是排查问题的第一眼

- 6 个指标卡片：**数值大字 + 状态色块**（绿=正常 / 黄=预警 / 红=告警），阈值判定颜色由处理域告警状态驱动

- 告警时：对应卡片红底闪烁 + 状态栏加"⚠"标记

### 页面 2 · 历史曲线

```
┌────────────────────────────────────────────────────┐
│  指标切换: [温度] [湿度] [烟雾] [电压] [电流]       │
│  ┌────────────────────────────────────────────┐   │
│  │  曲线区 (lv_chart)                         │   │
│  │  ▲ 温度(℃)  最近 5 分钟                    │   │

│  └────────────────────────────────────────────┘   │
│  图例: ━ 滤波值  ┈ 原始值                          │
└────────────────────────────────────────────────────┘
```

- 数据源：**内存环形缓冲**（最近 60s，处理域已维护）秒级实时 + **SQLite node_data**（历史 5 分钟/按需查询）——两级结合，实时看缓冲、翻历史查库
- 可选叠加原始值曲线（`raw_*`），直观对比滤波效果——**双保留的落地展示**
- 指标切换只换数据序列绑定，不重建 chart

### 页面 3 · 告警记录

- 列表页：从 `alarm_log` 倒序查最近 N 条
- 每行：时间 + 节点 + 指标 + 级别（⚠黄/🚨红）+ 值/阈值 + 状态（进入/恢复）
- 高亮当前仍处于 ALARM 的条目；可"全部清除已读"（只清 UI 标记，不动 DB）

### 页面 4 · 系统状态（调试页）

- 网关 IP / 运行时长 / MQTT 连接状态与重连次数 / 磁盘剩余 / 在线节点列表
- 用途：现场排障第一站，也是演示视频里体现"工程化"的镜头

**页面切换方式（二选一，建议都做）：**
1. 按键（input 子系统驱动，见 §6 驱动规划）——GPIO 按键翻页/确认
2. 触摸（如屏幕带触摸，ft5x06 等，Linux input 事件）

## 3. 显示驱动适配（framebuffer）

- 正点原子 MINI 的 LCD 是 **RGB 并口（LCDIF 控制器）**，Linux 下映射为 `/dev/fb0`，800×480 RGB565
- LVGL 显示驱动实现 `flush_cb()`：把 LVGL 输出的像素块 `write()` 到 fb0（或 mmap 后 memcpy）
- **双缓冲（RGB565 ×2）**：`800×480×2B = 768KB/缓冲`，两块 1.5MB——i.MX6ULL 512MB DDR 毫无压力
  - 作用：交替 flush 避免画面撕裂（tearing）
- 性能：`lv_disp_drv` 配 FULL_REFRESH 或 PARTIAL + 脏矩形模式；数据变化只重绘脏区，不是整屏重刷

> 面试点：**LVGL 只画"脏矩形"，flush_cb 把脏区刷到 framebuffer**——这是嵌入式 GUI 省带宽的核心机制，背下这个能答很多衍生问题。

## 4. UI 与数据线程对接（解耦设计）

```
处理线程 ──(写)──► 共享快照 struct node_snapshot（每节点一份）
                        │  node_id / values[5] / status / level[5] / last_update
UI 线程  ──(读)──► 定时轮询快照 → 刷新控件
```

**关键设计：**

| 项 | 方案 | 理由 |
|---|---|---|
| 数据载体 | **共享快照**（每节点一份结构体），不是队列 | 队列消费即消失，UI 需要"当前最新值"，快照是覆盖写、始终保有最新 |
| 同步 | 互斥锁保护，**临界区只做 memcpy**（微秒级） | 不持锁做任何控件操作——锁内重绘会卡住处理线程 |
| 更新频率 | 数值 500ms / 曲线 1s / 时间 1s | 环境量 2s 才来一条，500ms 轮询足够，避免无谓重绘 |
| 刷新触发 | `lv_timer` 定时器回调里读快照→`lv_label_set_text_fmt()` | 文本变了 LVGL 自动标脏重绘；没变不重绘（零开销） |

**为什么不用"UI 直接读 Modbus 数据"或"队列推送到 UI"：**
- 快照是"订阅-拉取"模型：UI 想刷就刷，不依赖消息时序；多页面（仪表盘/曲线）可以同时读同一份快照
- 队列是"推送-消费"模型：一个消费者拿走了别人就拿不到，不适合多页面共享

## 5. 刷新策略（60Hz 的正确理解）

**60Hz 是屏幕的时序上限，不是"每帧都要全量重绘"。** 实际刷新分三档：

| 层级 | 频率 | 内容 |
|---|---|---|
| LCD 物理刷新 | 60Hz | 硬件级，LVGL 不管——fb0 自己扫 |
| LVGL 重绘 | 事件/数据驱动 | 只有脏区重绘；数值 500ms、曲线 1s 触发 |
| 数据更新 | 500ms / 1s | lv_timer 驱动，读快照刷新控件 |

- LVGL 内部 `lv_tick_inc()` 由系统 timer 驱动（如 1ms），保证动画/长按等时间逻辑正确
- 仪表盘页面**不做动画**（数字跳变即可），省 CPU 也给演示加分——"低刷新开销"本身是优化点
- 唯一需要高帧率的是页面切换过渡（如 200ms 淡入），可选，量力而行

**资源预算（i.MX6ULL @528MHz）：**

| 项 | 预算 |
|---|---|
| 双缓冲 | 2 × 768KB ≈ 1.5MB |
| LVGL 堆（lv_mem） | 1~2MB（8.0 默认静态池可调） |
| CPU | 常规页面 < 20%，曲线页 < 40%（估算，实测调） |
| 线程 | UI 独立线程，优先级低于采集/处理（数据不因 UI 卡顿而丢） |

> 面试点：能说出"LVGL 只重绘脏矩形、UI 线程优先级低于采集线程"，说明你想过资源竞争问题，而不是只会调 API。

## 6. 面试价值点

1. **LVGL 移植三件套**：flush_cb / input read_cb / lv_tick_inc——GUI 库移植的标准动作
2. **脏矩形刷新机制**：为什么省带宽、怎么和双缓冲配合
3. **快照 vs 队列**：多读者场景下数据结构选型的判断力
4. **线程优先级设计**：UI 可以卡，数据不能丢——工业应用的正确取舍
5. **多页面数据源两级**：内存缓冲（实时）+ SQLite（历史）组合，展示层不背存储压力
6. **原始值叠加显示**：把存储域"双保留"变成看得见的功能

**简历 bullet 参考：**
> 基于 LVGL 实现 800×480 多页面监控界面（实时仪表盘/历史曲线/告警/系统状态），fb0 双缓冲直驱，脏矩形按需重绘；UI 线程通过共享快照与处理线程解耦，数值 500ms/曲线 1s 低开销刷新。
